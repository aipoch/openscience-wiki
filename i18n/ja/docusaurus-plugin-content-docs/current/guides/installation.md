# インストールとアップデート {/* #installation-and-updates */}

ほとんどのユーザーは、GitHubリリースからデスクトップパッケージをインストールする必要があります。 貢献者、または最新のコードをテストする人、またはソースからアプリを実行できます。 Electronデスクトップクライアントは、認証されたローカルブラウザインターフェイスを提供する共有ノードバックエンドに接続します。

<PlatformGuide />

**現在のパッケージ:** [v1.3.4 アセット](https://github.com/aipoch/open-science/releases/tag/v1.3.4)には、デスクトップインストーラ、スタンドアローンCLIアーカイブ、Linux CLI `.deb`/`.rpm`パッケージが含まれます。 意図したインストールタイプとアーキテクチャを選択し、同じリリースからチェックサムを確認します。 **Settings → General → Command line tool → Install command**でデスクトップランチャーが残っています。

## インストール方法の選択 {/* #choose-an-installation-method */}

### デスクトップインストーラをダウンロード {/* #install-the-desktop-app */}

1. [Open-Scienceリリース](https://github.com/aipoch/open-science/releases) を開きます。
2. お使いのオペレーティングシステムとCPUアーキテクチャに合ったパッケージをダウンロードしてください。
3. インストーラーとインストールが完了したライセンスを読んで、アプリを起動します。 5ステップのセットアップウィザードが最初の実行で開きます。
4. オペレーティングシステムが署名されていないアプリをブロックする場合、公式のAIPOCH GitHubリポジトリから再度ダウンロードし、ソースをチェックした後にプラットフォームのセキュリティプロンプトに従ってください。

**アセット** からリリースに添付されているので、自動的に生成されたソースコード ZIP ではなく、 選択します。 可用性は、リリースの公開資産に依存します。

Homebrew をインストールすることもできます。

~~~bash
brew install --cask open-science
~~~

インストール先にはアプリケーションを保存します。セットアップウィザードの **Data location** には研究ファイルと実行環境を保存するため、それぞれ別に設定します。インストール後は[初回設定](onboarding.md)に進んでください。

### スタンドアローンCLIを使う {/* #standalone-cli */}

ターミナル/ブラウザのインストールでは、[v1.3.4](https://github.com/aipoch/open-science/releases/tag/v1.3.4)からマッチングスタンドアローンCLIアーカイブをダウンロードしてください。 ノード、バックエンド、Web UI をバンドルします。 完全なディレクトリを抽出し、その後、[CLI セットアップ](../reference/cli.md#terminal-setup)に従ってください。 CLIを保ち、同じインストールからバックエンドを一緒に保持します。

#### ホーム醸造 CLI {/* #homebrew-cli */}

Homebrew CLIを`brew install aipoch/tap/open-science`でインストールまたは管理し、デスクトップの樽とは別にします。 Homebrewが提供するバージョンをチェックしてください。 GitHub リリースの後ろに、式が遅れる可能性があります。 インストールはシステムサービスを開始しません。 ランチャーが競合している場合、`type -a open-science` を調べて、そのインストールに `"$(brew --prefix aipoch/tap/open-science)/bin/open-science"` を使用します。

#### Linux CLIパッケージ {/* #linux-cli-packages */}

Linuxターミナル/ブラザーの使用のために、**オープン・サイエンス・クライエント**を、**エイポックオープンサイエンス**デスクトップのパッケージから別に選びます。 [v1.3.4 アセット](https://github.com/aipoch/open-science/releases/tag/v1.3.4)からマッチングパッケージと`CLI-PACKAGE-SHA256SUMS.txt`をダウンロードし、インストール前に確認します。

| 流通・建築 | v1.3.4 CLIアセット |
| --- | --- |
| Debian / Ubuntu, x64 | `open-science-cli_1.3.4_amd64.deb` |
| Debian/Ubuntu, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64, ARM64 | `open-science-cli_1.3.4_arm64.deb` |
| フェドラ、x64 | `open-science-cli-1.3.4-1.x86_64.rpm` |
| フェドラ、ARM64 | `open-science-cli-1.3.4-1.aarch64.rpm` |

適切なパッケージマネージャでダウンロードしたファイルをインストールします。 これらの例は x64 を使用します。 ARM64 ファイル名を適切に使用してください。

```bash
# Debian / Ubuntu
sudo apt install ./open-science-cli_1.3.4_amd64.deb
# Fedora: use this instead of the apt command
sudo dnf install ./open-science-cli-1.3.4-1.x86_64.rpm
```

`open-science-cli start --no-open` を実行し、`open-science-cli status --json` を実行します。 実行したら、認証されたローカルWebインターフェイスを開くには、`open-science-cli url`を使用します。 URL をプライベートに保ちます。 [CLI セットアップ](../reference/cli.md#terminal-setup) では、モデル構成と `doctor` チェックを続けて、`open-science` を `open-science-cli` に置き換えます。

パッケージは、Node、バックエンド、Web UI をバンドルします。 Python/Rをインストールしたり、自動起動したシステムサービスを作成したりしません。 OSのクレデンシャルストアとサンドボックスの前提条件はまだ適用されます。 [ヘッドレス Linux 資格情報](../reference/server.md) を参照してください。 デスクトップランチャーがインストールされている場合は、`open-science-cli` を明示的に使用してください。

パッケージをアップグレードまたは削除する前に、作業を終了し、**パッケージから始まるすべてのプロファイル**を停止します。 apt/dnf でダウンロードしたパッケージをインストールします。 このインストールで設定されているAIPOCH apt/dnfリポジトリはありません。 パッケージ除去は、研究データと資格情報を保存します。 [公式パッケージガイド](https://github.com/aipoch/open-science/blob/v1.3.4/docs/standalone-runtime.md#linux-cli-distribution-packages) は、コマンドの競合とプラットフォームの要件について説明します。

### ソースから実行 {/* #run-from-source */}

Git、Node.js 24、npm、およびElectron用のプラットフォームビルド前提条件が必要です。 アプリケーションにエージェントフレームワークをインストールまたは選択します。 インストール中に、リポジトリはPrisma Clientを生成し、アプリパッチを適用し、電子ネイティブ依存関係を準備します。

再現可能なソースのインストールには、依存関係をインストールする前に、[変更履歴](../changelog/v1.3.4.md)から意図したリリースタグを選択します。 デフォルトのクローンは、固定リリースではなくブランチを追従します。 選択したタグ、ソースコミット、ランタイムのバージョンを録音して、別の人が環境を再現できるようにします。

交換する `RELEASE_TAG` 選択したリリースに示す正確なタグ(そのリードを含む) `v`)... `--branch RELEASE_TAG --depth 1`を省略する代わりに、継続的な開発に従うため。 そのチェックアウトは、デフォルトのブランチに従います。

```bash
git clone --branch RELEASE_TAG --depth 1 https://github.com/aipoch/open-science.git
cd open-science
npm install
npm run dev
```

生産ビルドをパッケージ化する前に、実行します。

```bash
npm run build
```

選択したタグのパッケージ.json と [スタンドアローンランタイムガイド](https://github.com/aipoch/open-science/blob/v1.3.4/docs/standalone-runtime.md) を使用して、ビルド対象と依存関係を処理します。 `npm run dev:web` は Node/Web エントリーポイントを開発しています。 `npm run dev`はデスクトップクライアントも用意しています。 独立した構成ディレクトリを使用して、テストデータを分離します。

### ローカルデータ {/* #local-data */}

セットアップウィザードは、アーティファクト、Notebookファイル、環境などの大規模な研究ファイルの管理されたデータ場所を示しています。 アプリケーション設定と会話履歴は、設定場所にあるままです。 研究データの場所の移動は、完全なアプリケーションバックアップではありません。 ソースリポジトリから分離してください。 [ストレージ](storage.md) を使用して、アプリが実行している間、手動で内部ファイルを移動するのではなく、再配置します。

## アプリが準備されていることを確認します。 {/* #installation-is-complete-when */}

アプリが開き、必須の環境チェックが通り、選択した Agent が使用可能かつ有効で、モデル接続が確認できれば、リクエストを実行できます。既定の Open-Science Agent はアプリに同梱されています。外部フレームワークを選ぶ場合のみ、別途インストールまたは検出が必要です。Python/Rのセットアップは、それらの言語を実行する作業だけに必要です。 CSV または PDF プレビューを開くと、Notebook の実行時間を検証しません。 [初回設定](./onboarding.md) 以降、[プロバイダーとローカルモデルのセットアップ](./providers.md) を実行します。

## アプリケーションの更新をチェックする {/* #choose-a-reproducible-version-and-update-deliberately */}

**Settings → General** では、インストールされたバージョンを読み込み、**Check now** を使用して、アップデートの可用性を確認します。 インストールする前に、リストされているバージョンを調べて、最初にアクティブな作業を終了します。 開発ソースビルドは、パッケージされたインストールとは異なる更新を報告することができます。 更新前に重要なエクスポート結果のコピーを保持します。 アプリケーションの内部データディレクトリの名前を変更しません。

1.0から`open-science update`が削除されます。 デスクトップコントロールや公式インストーラーを通じてアプリを更新し、インストーラー/パッケージマネージャでCLIインストールを更新します。 **Check now**が公開されたリリースをまだ提供していない場合は、公式リリースページを確認してください。 設定を削除したり、アプリをリセットしたりすると、更新チャネルをプロモーションしません。

<PlatformContent platform="macos">

**更新する前に Open-Science をインストールしてください** が現れた場合は、読み取り専用の場所からアプリが実行されます。 **「アプリケーション」にインストール** を選択するか、Finder でアプリを移動します。 インストール後、**再起動** またはこのコピーを終了し、アプリケーションで 1 つを再オープンし、更新を再度確認します。 **このまま使用**は現在のコピーを開いた保ちます; 更新可能場所を作らない。 インストールが失敗した場合は、再試行する前に表示されたエラーに従います。

</PlatformContent>

<PlatformContent platform="windows">

既存のデータを再インストールします。 データ問題の後に新しいスタートを意図的にする必要がある場合は、[ローカルWindowsデータをリセットする](troubleshooting.md#windows-data-reset)を参照してください。 この別々のツールはデータを削除します。 通常のアップデートではない場合もございます。

</PlatformContent>

| 源の取付け | 確認する `node --version` そして、 `npm --version`とそれ `npm install` 完了しました。 中断された依存関係の取付けを再試して下さい。 |

## v0.31.0の後のプロダクト命名 {/* #product-name */}

現在のインターフェイスと新しいパッケージは、**Open-Science**を一貫して使用しています。 アップグレードは、既存のインストール名と場所、研究データ、資格情報、設定を保存します。 `Open Science`を含む古いインストールパスは、アップグレードの失敗ではなく、 新しい表示名と一致させるためにデータ フォルダーの名前を変更したり、移動したりしないでください。

## 1.0へのアップグレードと互換性の理解 {/* #version-compatibility */}

1. アクティブな研究を終了し、構成ディレクトリと任意の別々の構成されたデータの場所をバックアップします。 1つの`.science`エクスポートは、プロファイル全体のバックアップではありません。
2. インストールを使用してデスクトップ/バックエンドのインスタンスを閉じて、公式インストーラーでアップグレードします。 オリジナルのプロファイル、データ、OS認証ストアを保管します。
3. バージョン、プロジェクト、セッション、ファイル、モデル、ランタイムを継続的に再オープンし、確認します。 バイナリダウングレードはデータをロールバックしません。 古いバイナリは、新しい保存されたデータを読み取らない場合があります。

1.0 は、既存の履歴アップグレードとインポートパスを保持します。バージョン番号はプロファイルリセットを必要としません。 [1.x 互換性ポリシー](https://github.com/aipoch/open-science/blob/v1.3.0/docs/compatibility.md)は、CLI/SDKとタスクの自動化インターフェイスを文書化し、有効な`.science`パッケージのインポートを転送し、プロファイルのアップグレードをサポートしました。 同じモデルの回答、サードパーティの可用性、または全研究セッションの決定的な再生、またはOS保護された資格情報のクロスプラットフォーム転送を保証するものではありません。 セキュリティは、最新の安定したリリースをターゲットに固定します。

## CLIをnpmにインストールする {/* #npm-cli */}

Node.js **22.13以降** は、公開された CLI/backend パッケージで使用できます。 ターミナルで、呼び出されたバージョンをインストールし、検査します。

```bash
npm install --global --include=optional @aipoch/open-science@1.3.4
open-science version --json
open-science help
```

次に、[ターミナル セットアップ](../reference/cli.md#terminal-setup) に従ってプロファイルを初期化し、バックエンドを起動し、モデルを構成します。 インストールだけでは、Python/Rをインストールしたり、ログインしません。 デスクトップまたはHomebrewのランチャーが同じコマンド名を既に使用している場合、続行する前にシェルが選択できるかどうかを調べます。 そのインストールをアップグレードする前に、インストールによって所有されるすべてのバックエンドを停止します。 オリジナルのパッケージマネージャでプロファイルとアップデートを保持します。

## インストールを通して更新に従ってください {/* #update-progress */}

**Settings → General**では、インストールされたバージョンを読み込み、**Check now**を選択します。 提供したリリースとアップデートダイアログのダウンロードと準備状態を確認します。 ダウンロード完了はインストール完了ではありません。 再起動後にインストールされたバージョンを確認します。

対応する安定版パッケージでは、**Automatically download updates** がバックグラウンド準備を制御し、初期状態では有効です。無効にして手動の確認・ダウンロードを続けることもできます。自動ダウンロードには、通信量による課金や制限のない接続であることの確認と、十分な空き容量が必要です。ネットワークの状態を確認できない場合、空き容量が足りない場合、または保存先に書き込めない場合は、手動で更新します。

| プラットフォーム | 適格な自動行動 | 手動取付けを使用するとき |
| --- | --- | --- |
| macOS | アプリを終了したときに準備完了したアップデートをインストールできます | 読み取り専用のボリューム、アプリの転送、書き込み不能なインストール、またはサポートされていないチャネル |
| Windows | ワークスペースの準備ができたら、次の起動のための更新を準備し、デスクトップはバックグラウンドでアイドルです | 準備はブロックされ、チャネルはサポートされていないか、またはインストーラは代わりに提供されます |
| Linux アプリイメージ | バックグラウンドで次の更新を準備します。 既存の AppImage パスを保持する | 更新キャッシュは不利で、スペースが不十分であるか、またはパッケージのフォーマットはサポートされていない |

アクティブな作業を終了し、Notebook のクリーンアップを終了するか、または再起動する前に完了させます。 ダイアログに従って**Restart to update**か**Open installer**を使用して下さい、そして版および元のプロジェクトを確認して下さい。 Linux DEBおよびスタンドアロンCLIの取付けは自身の[設置チャネル](#manual-update)に続きます; ウェブワークスペースはデスクトップの自動更新装置ではありません。

準備が失敗するか、または自動取付けが利用できなくなったら、**Installation instructions**および公式のパッケージを使用して下さい。 クリーンアップ中にアプリが閉じられているように強制しないでください。

## 更新を手動でインストールする {/* #manual-update */}

更新画面の **Installation instructions** を開きます。パッケージがなければ **Download from website**、確認済みのダウンロードがあれば OS に応じて **Show in Finder**、**Show in File Explorer**、**Show in file manager** を使います。アプリ終了時もそのフォルダーを開いておきます。

作業を保存し、進行中のインストールや後処理の終了を待ちます。macOS は DMG を開くか ZIP を展開して Applications 内の Open-Science を置換。Windows は既存フォルダーへインストール。Linux は対応 DEB をインストールするか AppImage を置換し、実行権限を維持します。実際の形式に対応する手順に従ってください。

ファイルが見つからない、または変わった場合は再ダウンロードします。場所の表示はインストーラーの実行ではありません。再起動後に **Settings → General** で版を確認し、元のプロジェクトとデータを点検します。独立 CLI の交換前は[全対象サービスの停止を確認](../reference/server.md#application-update-behavior)します。

## Windows 更新後に研究データを確認する {/* #windows-update-data */}

v1.0.6 の Windows インストーラーはアプリの隣にある研究データを保持し、深いフォルダーパスへのインストールを修正しています。実行中の作業を終え、重要なプロジェクトをバックアップしてから公式インストーラーで更新します。再起動後に **Settings → Storage** を確認し、既存プロジェクトのファイルを開けることを確かめて作業を再開します。

この修正はバックアップの代わりにはならず、管理対象データを手動で移動してよいという意味でもありません。保存先の変更には[ストレージ設定](storage.md)を使います。

## ハンドル更新準備ブロッカー {/* #update-preparation */}

アップデートをインストールする前に、アクティブな作業を終了します。 準備名がブロックされたプロセスの場合、関連するプログラムを正常に閉じて、再試行します。 関係のないプロセスをキルトに強制することを避けて下さい。 v1.0.8は複数のmacOSおよびWindows占有率点検を訂正します; ダイアログの残りのブロッカーはまだ注意を必要とします。

自動インストールが利用できない場合は、**Settings → General**の手動インストールヘルプリンクを使用して、一致する公式パッケージをダウンロードし、チェックサムを確認します。 再起動後、インストールされたバージョンと元のプロジェクトを確認します。 回復が失敗したら、診断ログを一般から収集して下さい; トラブルシューティングのエラーが残っています。

### macOS差分ダウンロード {/* #differential-updates */}

v1.2.0 から、サポートされている macOS アップデートは、アプリイメージのブロックのみ変更できます。 そのパスが利用できなくなったり検証できない場合は、updater はフルパッケージに戻ります。 より大きなダウンロードは、それ自体が失敗するわけではありません。 ダウンロード完了、更新準備完了、再起動後にインストールされたバージョンを確認します。 自動インストールは[プラットフォームとチャネル条件](#update-progress)に従います。

## インストールがブロックされるとv1.3.0から更新 {/* #update-from-130 */}

v1.3.0 は、アクティブな作業が終了した後であっても、別のプロセスがインストールを使用していると述べた場合、その更新担当者は、外部ブロッカー用のアプリ所有の背景プロセスを誤ったことがあります。 v1.3.1公式パッケージをダウンロードして、Open-Scienceを完全に終了し、バックグラウンドサービスを停止し、[手動インストール手順](#manual-update)に従う。 CLI管理プロファイルについては、ファイルを交換する前に[サービスの状態および停止](../reference/server.md#lifecycle-commands)を確認してください。

アプリを再オープンし、**Settings → General**でv1.3.1を確認し、元のプロジェクトとデータの場所を確認します。 プロフィールや研究データが保持されます。 この修正は、v1.3.1から始まる更新に適用されます。 新しくダウンロードしたパッケージは、v1.3.0 で実行中の updater を変更できません。
## v1.3.4のWindowsアップデート {/* #windows-134 */}

v1.3.4は、更新の準備中に、組み込みのエージェントと画像ヘルパーをアプリ所有プロセスとして認識します。 旧バージョンアップが作業終了後、これらをブロッカーとして報告する場合、[公式マニュアルインストーラ](#manual-update) ではなく、繰り返し強制プロセスを強制的に終了します。 リリース後にバージョンと元のプロジェクトを確認します。 新しいパッケージは、古いバージョンで実行中の更新者を修復することはできません。

Windows の更新は v1.3.4 の密集したインストーラーの deltas を元通りにします。 v1.3.3はフルインストーラーを使用しました。 フルパッケージのダウンロードはまだフォールバックであり、それ自体が故障を示すことはできません。
